As you asked, no code yet. I only saved your working rules and the deadline to my memory so they carry over if this session restarts.
1. What I understand the task to be

* The goal: build a forecasting setup for Ukrainian air raid alerts. At a fixed time t it gives a probability (or count) for a target we define, over a window h after t. It should be built on the freshest data we can get and scored on the most recent period.
* The main rule is no leakage. Every input at time t must have been knowable at t. In particular, an alert still running at t has no end time yet. So we rebuild the "state at t" from start times only and never read `finished_at > t`. A pytest will check this automatically.
* Evaluation is time-ordered. We train only on the past and test on what comes after, using walk-forward evaluation. That means: train on everything up to week N, forecast week N+1, step forward a week, repeat. This shows how the model would have done if deployed live. The final test period is the most recent stretch, and we score it only once.
* The model only counts if it beats simple baselines. These are climatology (the average alert rate for this hour of the week in this region), persistence (whatever is happening now continues) and seasonal naive (same as this time last week). The metrics must fit the target. For probabilities that means the Brier score: the average squared gap between the predicted probability and what happened (0 or 1), where lower is better. We also check calibration: when the model says 30%, do alerts actually happen about 30% of the time?
* Deliverables: one-command reproducible pipeline, README with a results table against the baselines, NOTES.md, public repo. Text/Telegram features come only after the core model works, under the same rule (only content published before t).
